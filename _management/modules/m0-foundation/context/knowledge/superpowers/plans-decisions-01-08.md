## 2026-07-23-ai-image-foundation.md（2026-07-23）｜ AI 图片基础（Kimi 规划 / Wan 生成 / 加密配置 / 审计）
- 摘要：为商品图生成建立"加密配置 + 持久化批次 + Kimi 规划 + Wan 生成 + 确定性渲染 + 双重审计"的基础链路，并以兼容门面渐进迁移旧富化逻辑。
- 决策要点：
  - 架构取舍：PipelineService 继续做编排者，但模型调用与图片状态下沉到聚焦服务；ProductImageGenerationService 保留为兼容门面，选"渐进迁移"而非一次性重构，降低回归风险。
  - 角色分离：Kimi 只规划与审计、绝不声称能生成图片；Wan 只负责基于淘宝/1688 参考图生成无文字图；主图与详情图参考严格分离，互不混用。
  - 密钥安全：用 Windows DPAPI（ctypes）加密落库并加 `dpapi:` 前缀；迁移期仍可读旧明文 DeepSeek 行；配置部分更新用可选字段，保存一个 key 不清除其他 key；API 只输出掩码。
  - 失败语义：缺 key 显式抛 ProviderNotConfigured，不返回空 dict、不生成 mock 图；provider 超时不重复提交任务（task id 先持久化再轮询），保证重试幂等；Wan 用有界指数退避轮询，且拿到 URL 立即下载（provider URL 会过期）。
  - 内容安全：规划层拒绝重复卖点、不支持的数字、缺参考、供应链违禁词；Wan 负向指令固定含供应链文本/logo/违禁声明/水印/错乱文字；渲染只允许 verified_copy/verified_numbers 落图。
  - 审计双轨：本地审计确定性把关（感知哈希去重、违禁文本、尺寸/可读性、主图/详情图数量、路径缺失或重复）；Kimi 视觉审计补一致性与场景检查，其失败标记"审计不可用"并阻断自动通过。
  - 硬约束：生成主图必须感知上互不相同；新品类必须停在"待图片审核"人工复审，未经批准不得声称"待上架"；provider 失败不得复用旧图（旧路径清空）。
  - 环境约束：本机无 Git CLI，以"跑测试 + 记录变更文件"代替提交，作为本仓库所有计划的通用约束。
- 里程碑/验收要点：
  - 全程 TDD：每任务先写失败测试再实现；每步跑全量回归，保证旧 1688/微信测试保持绿。
  - 数据模型：image_batches/image_assets 新增不破坏旧商品行；(batch_id, kind, position) 唯一约束；资产状态不靠文件名推断。
  - 最终验收：富化流程对新品类止于"待图片审核"，未过审绝不进入"待上架"。

## 2026-07-23-image-review-workbench.md（2026-07-23）｜ 图片审核工作台（Next.js 前端 / 审核 API / 上架记忆）
- 摘要：把选定的首版设计落成真实运营工具：显式审核/记忆 API + 应用壳/工作流条/紧凑队列/图片检查器，保留旧任务端点与会话轮询。
- 决策要点：
  - 前端取舍：定位是运营应用而非落地页，核心工作流按钮必须可用；按用户选定的首版设计实现，弃表格优先的大前端（应用壳 + 工作流条 + 紧凑队列 + 检查器）。
  - 品类记忆状态机：新品类需连续两次"首过批通过"才切换 auto；单次商品驳回不降级，连续两次图片相关平台驳回才退回 manual；资质/禁售品类失败只记不可变事件，绝不训练自动绕行。
  - 审核契约严格化：驳回必须选自枚举 reason；"批准整组"要求组内全部资产已批准；驳回单资产只置该批回 waiting_review，不动其他已批准资产；批准整批才更新记忆并转"待上架"。
  - 单资产再生成：regenerate 只重置选中资产、递增 attempt、用保存的 plan + 驳回原因重跑工作流并只重审该资产，避免整批重做。
  - 前端状态映射：getWorkflowStage 按 published(有真实链接)→平台审核→draft→图片审核→生成→1688→淘宝→选品顺序判定；"已上架但无链接"不算 published、"待确认上架"归 draft，防把草稿当已发布。
  - 布局硬约束：156px 深色侧栏 + 48px 连接栏 + 无框主工作区；卡片圆角 ≤6px；禁嵌套卡片/渐变/紫色/超大标题；主图 1:1、详情图 3:4 稳定比例，审批控件不改变布局尺寸；390px 窄屏切紧凑顶导航 + 单列，文字不随视口缩放。
  - 密钥与会话：key 只在系统设置录入、仅回显掩码，空输入保留现有 key；"测试连接"走后端健康检查不暴露 key；复用既有微信/1688/淘宝会话（不重新登录）；上架记忆视图首版只读。
  - 操作约束：既有 11 个动作"移动不删除"；队列行选中本身不触发网络任务。
- 里程碑/验收要点：
  - 每任务 TDD + 后端全量回归 + 前端 Vitest/生产构建；最终跑 compileall 防语法回归。
  - 最终验收：1440x1024 与 390x844 双视口无文字重叠、五主三详情图尺寸稳定；真实交互（批准/驳回/理由/单资产重做）刷新页面后持久化。

## 2026-07-23-multi-channel-product-sourcing.md（2026-07-23）｜ 多渠道选品（三源轮换 / 断点续跑 / 365 天去重）
- 摘要：让每次选品在微信机会、优米云、考拉家三源间轮换，各源从持久化 checkpoint 断点续跑，跨平台 365 天去重，当前源填不满时顺延下一源。
- 决策要点：
  - 轮换机制：平台按 微信→优米→考拉家 顺序，每完成一次运行推进"下次启动源"指针（与同轮内兜底顺序无关，重启后仍存活）；板位/滚动位置按源独立存 cursor，从断点续跑。
  - 身份与去重：身份强度排序——真实源 ID/URL > 图片感知哈希 > 归一化标题；去重窗口 365 天；只有入选商品才写入 products/product_library，被拒临时候选不占去重指纹，避免污染后续选品。
  - 品类风控分层：先跑确定性硬过滤（日用品白名单、鞋服/食品/药品排除、低退货分），只有歧义分类/退货风险才调 Kimi 判定——省调用成本且行为可预测；图片哈希用保守汉明阈值防误杀。
  - 浏览器会话：优米/考拉家共用用户便携 Chrome（精确可执行路径 + 精确 profile）+ 单一 CDP 端口，每平台只复用一个 tab、绝不重复开 tab；隐藏启动无终端窗口；登录/验证页暴露给用户处理；状态检查只查 CDP 不启 Playwright。
  - 节奏风控：浏览步进 3-6 秒，每次验证事件后增大延迟（自适应延迟持久化），降低被平台风控概率。
  - 板位策略：优米 9 榜、考拉家 3 榜按配置顺序轮换，每板位最多取 30 个新行；解析须含标题、图、源 ID/链接、板位、排名/销量信号、类目、退货信号。
  - 缺额语义：当前源新鲜库存不足时如实报告 shortfall，不拿已见重复品凑数；下一源继续补。
  - 前端取舍：一键选品仍是主命令，不让用户每轮手选平台；新增"打开选品浏览器"单按钮复用既有会话，前端只展示通道/起点/下一源/当前板位/选中数与缺额。
- 里程碑/验收要点：
  - 连续四次运行启动顺序必须为 微信→优米→考拉家→微信；每源从保存的板位/滚动断点续跑。
  - 跨源去重生效：任一源已选商品在其他源 365 天内被跳过；缺额如实上报；便携 Chrome 无重复 tab、无重复终端窗口。
  - 入选商品必须继续走通淘宝、1688、Kimi/Wan、图片审核、草稿、最终发布全链路，无契约回归。

## 2026-07-23-platform-repair-publishing.md（2026-07-23）｜ 平台修复与发布（驳回解析 / 定向修复 / 发布状态机）
- 摘要：解析微信平台驳回文本，可修复类别自动定向修复（每商品最多 2 次）、同 tab 重提，并把发布状态收敛为"真实链接才算已上架"的严格状态机。
- 决策要点：
  - 可修复性策略：UploadResult 结构化（驳回文本/类别/失败图位/平台状态）；可修复类别=图片、图片文案、图片重复、图片场景、可编辑商品文本；人工类别=资质、禁售类目、商标/IP、未知素材来源、账号限制——资质类永不调 Kimi/Wan，绝不自动绕过平台规则。
  - 修复次数硬上限：图片修复每商品提交恰好 2 次，第 3 次阻断转"人工审核"；只修复失败资产，已批准资产保持字节级不变；尝试记录唯一约束 (product_id, batch_id, attempt_no)。
  - 定向修复闭环：Kimi repair prompt 输入平台原文+失败图+原 plan+已核实数据+允许变更面，输出必须指名资产 ID 且不得新增未核实事实；生成走版本化文件名（如 _r2.png），审计通过前不覆盖旧文件。
  - 同 tab 复用：微信/1688/淘宝各复用一张既有页面；修复仅移除→上传→等预览完成替换指定 slot，其余图片与页面不动；最终发布点击前须清空页面校验错误。
  - 发布状态机：单一转移函数 apply_upload_result 集中处理 草稿/审核/已过审无链接/驳回/资质/已上架 各态；product_link 只在 status=="published" 且非空时写入；一切非 published 转移清空旧链接；从真实商品行/详情页读平台状态并存平台原文与截图，绝不凭页面导航推断"已上架"。
  - 记忆联动：草稿保存/提交/已上架/驳回/修复尝试/修复成功/修复耗尽均记不可变事件；品类连续两次图片驳回退回 manual。
  - 验收纪律：真实商品验证（product 4/5），不为制造驳回而伪造平台违规；字段校验用下拉选值（产地/材质/直径/形状/拍卖价/量产/SKU 价/库存 10000/至少一张详情图）。
- 里程碑/验收要点：
  - 状态边界测试三例：草稿保存→待确认上架且无链接；published 无链接≠已上架；真实链接才置"已上架"。
  - 最终验收：全量测试绿 + 后端 /health ok + 前端 200；无任何商品在无真实链接时被标"已上架"。

## 2026-07-28-category-aware-main-image.md（2026-07-28）｜ 品类感知主图（主题 / 安全区自动布局）
- 摘要：用品类主题 + 源图"最不繁忙区域"自动排版替换固定第一主图覆盖层，文案仍以既有商品策略为唯一来源，其余图片一律不动。
- 决策要点：
  - 范围收敛：只允许改动第一张主图，其余已归档图片保持字节级不变——用"变更前后哈希一致"作为硬验收，降低回归面。
  - 主题选择确定性：select_main_theme 按 茶/家居/数码/母婴/清洁/户外 等品类规则确定性选主题与配色，弃"一套固定样式套所有品类"的做法（固定覆盖层易与品类调性冲突）。
  - 文案来源单一：主图文案仍由既有商品策略产出（eyebrow/headline/subhead/badge），渲染层不新造卖点，保证可溯源。
  - 安全区自动布局：choose_main_text_layout 对左/右/顶部居中三个候选区做灰度边缘/方差打分，选最不繁忙区域放置紧凑文字层级（含文字阴影与紧凑半透明行背景），避免文字压住产品主体。
  - 渲染与真实性硬约束：输出 1024x1024 PNG、局部对比处理；标题尽量 4-10 个中文字、最多三种主色；绝不虚构数字/材质/认证/功效/销量/折扣，绝不输出供应链词。
- 里程碑/验收要点：
  - 仅重生成 image 1；对商品 2 号及以后图片先记哈希、再验证不变。
  - 视觉检查：层级、对比、产品遮挡、真实性、违禁词；全量前后端测试套件保持绿。

## 2026-07-29-production-workflow.md（2026-07-29）｜ 生产工作流（持久化任务 / 报价生图分离 / 双闸门 / 异常中心）
- 摘要：以 SQLite 工作流任务为真相源，报价与生图分离成独立 worker，用图片质量闸门 + 上架就绪闸门做质量关卡，并提供异常中心与严格的发布真实性。
- 决策要点：
  - 任务即真相源：SQLite workflow_jobs 是持久化真相源，Product 字段只是面向用户的投影；报价/参考/生图各为独立 job，报价先行提交（含价格/运费事务），生图失败不得阻塞其他商品报价（按商品隔离）。
  - 双 worker 分离：单一浏览器 worker 消费 阿里/淘宝 阶段、独立生成 worker 消费 AI 图片阶段——图片故障与浏览器故障互不拖垮对方；启动时自动恢复过期租约任务，幂等迁移旧商品态。
  - 图片质量闸门：ImageQualityGate 产出 approve/exclude/rework；闸门未过的批次不进图片审核队列；exclude 对当前批永久生效无需补图；rework 只入队被驳回图位并携带驳回原因；最终批次只用已批准且未排除文件。
  - 上架就绪闸门：ListingGate 产出结构化 blockers（缺报价证据/SKU/已批图/必填属性/未决风险），并用于"可上架"查询与上传动作——资格判定集中成服务，而非散落在各处状态判断。
  - 发布真实性：保留 草稿已存/待确认/平台审核/已过审无链接/链接已验证 五个独立状态；仅"链接非空且有效"才允许"已上架"。
  - 前端：新增"异常中心"（登录/验证/报价/参考/图片/AI/平台 错误过滤）；工作台分开展示报价与生图进度，报价完成即显示"已报价/待生图"；图片审核视图只含已过图片闸门的商品。
  - 自动化边界（硬约束）：复用既有页面/CDP 不重复开 tab；绝不提交真实 1688 订单；绝不解决或绕过验证挑战；绝不自动发送外部客服消息；自动化验证期间绝不真实发布商品。
- 里程碑/验收要点：
  - 迁移与恢复：可恢复旧商品状态转幂等 job；旧汇总任务标记 superseded 但不删审计历史；应用启动自动恢复过期租约并拉起 worker。
  - 端到端冒烟（不发布）：选品→报价持久化→生成→图片闸门→图片审核→上架闸门 全流程跑通，且验证全程无真实订单、客服消息、验证操作或商品发布发生。

## 2026-07-30-automatic-sourcing-implementation.md（2026-07-30）｜ 自动选品落地（自动调度 / 板位频率 / 评分 / 跨渠道合并）
- 摘要：让合格非品牌商品从三源自动进入"待选品审核"：重启安全的板位调度器 + 持久化证据 + 硬过滤与 100 分评分 + 跨渠道合并，下游一律留人工闸门。
- 决策要点：
  - 边界隔离：自动选品只做 发现→过滤→评分→去重→创建"待选品审核"记录，绝不启动淘宝参考/1688 报价/AI 生图/微信草稿/发布；硬断言每个自动入库商品=待选品审核、未询价、未生成、零 workflow job，防止自动化悄悄越界。
  - 调度持久化：SourceBoardState（唯一 (platform, board)，含频率组/间隔/游标/上次 item id/失败计数/节流级别/暂停原因/证据 JSON）+ ProductSourceEvidence（唯一 (product_library_id, platform, board, source_item_id)，含排名/评分/首末次出现），重启从最后 checkpoint 恢复、seed 幂等。
  - 频率分级：high=2 小时、medium=6 小时、low=每天；板位清单是不可变 frozen spec，且显式排除品牌竞争类板位（如"品牌竞争大盘"）——只采无品牌标的的板位。
  - 过滤与评分：品牌/旗舰/官方/授权/联名/明星 IP/美妆/医疗功效/授权商品/易碎/重安装/版型类硬过滤；缺标题/URL/有效商品图视为硬摄入失败；评分 100 分制=趋势 35/利润 30/售后 20/供应 15；AI 不可用时 classify 返回 needs_ai_review 而非放行；真实询价前用保守历史价估算并标"待真实询价"。
  - 跨渠道合并与学习：365 天指纹只建一条 Product；跨渠道命中合并 evidence（更新 rank/score/seen_count 不新建商品）；驳回写入品牌黑名单 + 回收记忆，批准存正向偏好但加分设上限、不得覆盖硬过滤；七类驳回原因枚举校验。
  - 调度器语义：run_due_once 单循环 claim→有界扫描→checkpoint→排下次→finally 释放；错误分类 waiting_login/waiting_verification/risk_control/page_changed/retryable；登录/验证/风控只暂停受影响平台，其他平台照跑；进程内锁防重叠；节流 0..4 级渐进退避 + 连续失败熔断、稳定期逐级恢复。
  - 状态与控制 API：/automation/status 返回 enabled/当前板位/今日计数（合格/品牌/重复/待 AI）/各平台节流与阻塞/下次运行；pause/resume 只改调度配置、绝不动商品工作流状态；不暴露 cookie/token/原始 HTML；手动 /tasks/source 保留为紧急扫描且证据带 trigger=manual。
  - 前端：紧凑"自动轮巡"面板（10 秒轮询轻量状态 API，绝不在该定时器里调 Playwright 登录状态）；手动按钮改名"立即巡检一次"，计数选择器仅限手动紧急扫描。
- 里程碑/验收要点：

  - 冻结时钟安全验收（2h/6h/24h 窗口）：合格→待选品审核；品牌/高风险→过滤；跨渠道重复→1 商品 2 evidence；登录阻塞→仅该平台暂停；重启→到期板位从 checkpoint 恢复；全程无报价任务、图片任务、微信草稿、发布提交或商品链接产生。

## 2026-07-31-sourcing-admission-gate.md（2026-07-31）｜ 选品准入闸门（准入与排名分离 / 只硬阻断 / 过滤可解释）
- 摘要：把准入从排名中彻底拆出——只有证据无效与硬风险才阻断，缺商业数据/AI 不确定的候选一律带注释进入人工选品审核，且每个自动过滤都有计数可查。
- 决策要点：
  - 准入与排名分离：classify_candidate 只负责证据有效性与硬风险阻断，score_candidate 只对已准入候选排序；删除 55 分质量阈值门槛——评分永远不决定能否进入人工审核，防止"低分漏好品"。
  - 只硬阻断：品牌/IP、食品、服装、医疗/美容资质、明确高退货、证据无效 仍是硬阻断；缺价格/退货率/1688 报价/供应商数/未知类目 一律不阻断，转为软风险 + needs_ai_review 注释，AI/缺商业数据只注解待人工审核记录、绝不静默丢弃。
  - 误杀纠正：未知拉丁型号 token（如 SW35）从硬阻断改为软风险；数字小数括号内容（如"20【2.0】"）认定为规格括号而非品牌改款——修正过严的品牌适配判定。
  - AI 不确定性落库：AI 输出原样保留到 candidate.ai_result 并重跑硬分类器，仅当硬分类器发现新硬风险才丢弃；否则入库并把 AI/合规警告写入 review_reason/brand_risk 供人工参考。
  - 过滤可解释：每个硬过滤都记 filter_reasons 计数（品牌黑名单单独计数 + CandidateDecision.reason 聚合），按板位存进采集证据并汇入周报 weekly.filters.reasons——"每个自动拒绝都有据可查"。
- 里程碑/验收要点：
  - 回归套件全绿：sourcing_candidates / pipeline_safety / sourcing_report / sourcing_scheduler(+api)，变更模块 py_compile 通过；重启后 /health ok 且自动选品保持启用。
  - 有界真实采样：复用共享浏览器与已登录板位、限 15 候选、不调报价/生图/草稿/发布端点；验收：硬风险仍被过滤、存在非硬阻断日用品时至少一个进入"待选品审核"、filter_reasons 解释每个硬拒绝。
