# DSH 对 Codex round-02 开发方案的裁决与收敛

> 轮次：round-03，归属 DSH。

> 范围：方案裁决与收敛，不写代码。最终给出可进入「开发启动任务拆解」的方案骨架。

## 一、对 Codex 四个分歧取向的裁决

### 分歧 1（模块化单体 + 单 Postgres 库 + 单一 migration head）——✅ 采纳
理由成立：半成品的「六物理库」并未形成独立服务边界（`api/services.py` 跨库聚合、`listing_gate`/`tagger`/`compliance` 跨模块 import），物理分库只增演进成本；M2 schema 漂移已实际造成 API 500。"单一迁移集"不是 100 店瓶颈。特别认可 Codex 对 `app_config` 同名异义（M0 系统配置 vs M1 领域配置）的拆解要求——这是新 schema 必须修的历史债。

**DSH 补充**：迁移策略明确为「**新 schema 建库为主，旧 SQLite 按可验证导入包迁入**，首次上线不求无损在线转换」。这意味着新仓库首日就建 Postgres，不背旧六库包袱；旧数据导入是「受控物料」，不是「必须一次性全量搬」。

### 分歧 2（tenant/account/shop 三级 + 账号级隔离 + 素材 bindings）——✅ 采纳
Codex 的 `asset_shop_bindings` 方案比 DSH 原「素材挂多 shop」更正确：用**绑定关系**而非复制/固化，保留「哪家店以何用途用了哪一版素材」的证据，支持撤销、店级审核差异与后续多主体隔离。

**DSH 采纳并补三点**：
1. `platform_accounts` 承载账号即隔离/限速/熔断/登录态元数据——同意，这与「隔离粒度=账号」一致。
2. 凭证原文进独立 secret 存储，业务库只存 `credential_ref` + 状态 + 脱敏值——采纳，见下文问题1裁决。
3. Data 所有权边界明确：业务主表带 `tenant_id`，账号/店铺产生的才带 `account_id`/`shop_id`，不机械塞三 ID——认可,避免冗余建模。

### 分歧 3（持久化流程状态机编排 + 队列执行叶子任务 + 人工闸门不占租约）——✅ 采纳，且优于 DSH 原倾向
DSH 原提议「独立 scheduler + 显式状态机」；Codex 更精确地提出**两层分工**：
- 业务因果（选品→素材→上架确认→托管确认→两次回读→ROI 回写）由持久化 `workflow_runs/workflow_steps` 状态机承载；
- 可重试单步由 M0 `WorkflowQueue` 执行（复用 enqueue/claim/complete/fail/recover 与错误码）。

人工闸门用「step 置 `waiting_confirmation` + 生成证据快照 + 结束当前 job + 乐观锁确认 API」表达，不阻塞其他租户/账号任务。**DSH 认可**：这解决了「人工确认如何在队列模型里表达而不阻塞全局」——正是 round-01 邀请里我抛给 Codex 的问题，它给出了正确答案。

### 分歧 4（先固化语义，再真实只读回读，最后真实写入）——✅ 采纳，并修正一处混淆

Codex 把「回读前置」细化成 P0-2 离线验证语义 → P0-3 真实只读回读 → P0-4 最小真实写入,并且明确「回读前置 ≠ 资金写入前置」。DSH 认可这个顺序。

**但 DSH 修正一处混淆**：Codex round-02 第 101 行说「若主链未就绪,UI 轨必须真机化」是在 M4 上架上下文;而 P0-3 的「真实只读回读」是 **M5 投放后台报表**的只读抓取,二者是**两个不同的 UI**:
- P0-3 抓的是**投放报表页**(M5) → 只读,验证账号级 profile/选择器/登录态/限流。
- M4 上架的 UI 兜底是**商品上架页** → 那是后面 P0-4 的事,且优先走 OpenAPI 主链。
两者不能混为「一个 UI 真机化」,否则会过早扩大范围。Codex 的分期表里 P0-3/P0-4 其实已隐含区分,但措辞在分歧4说明里滑了。DSH 特此钉死:**P0-3 目标只是报表只读回读,不碰上架 UI**。

## 二、对 Codex 丢回给我的 3 个问题的裁决

### 问题 1：本地自托管下，凭证原文的存储形态
**DSH 裁决**：一期用**本地受限加密文件存储 + 独立目录**（非 git 追踪、权限受限、主进程外读写），通过一个 `secret_store` 抽象接口访问。理由：
- 本地自托管起步，引入完整 secret service（如 Vault）是过度设计;
- 独立加密库比「塞进业务 schema」更安全,且后续换 Vault/云 KMS 只需换 `secret_store` 实现;
- 凭证不落 API 响应/日志/migration seed（沿用半成品 `_redact_text` 惯例)。
- 在 P0-1 把 `secret_store` 接口与本地实现一起交付,便于 P1 加固时可替换。

### 问题 2：M4 OpenAPI 业务接口是否完整可用
**DSH 裁决**：把「M4 OpenAPI 契约核对」列为 **P0-4 的前置硬任务**（对应 Codex 原 P0-4），不预设「主链一定可用」。
- 在 P0-4 前，安排一个独立小里程碑「核对并接线 M4 8/9 业务接口官方路径与字段（T2~T4）」；
- 若核对后主链可用 → 上架走 OpenAPI 主轨；若任一关键接口不可用/未开放 → **声明上架兜底轨为 P0-4 的必做真机项**，不能默认它已能兜底（复核已证 `ui_fallback.py` 是 `MockPageOps` 零浏览器）。
- 决策点依赖真实账号/官方文档实测，故不得在 P0-1 冻结成「主链必成」。

### 问题 3：报表可抓字段与两次回读时间窗口
**DSH 裁决**：**P0-3 实测后才进入配置，不预设常量**。
- 先在 P0-3 用真实账号抓一次报表，登记「实际可解析字段清单」与「两次回读的最小稳定间隔观察值」;
- 把这些写入配置（`report_interval_s` 等已存在），并留 `REPORT_MANUAL` 兜底;
- 时间窗口不写成魔法数字,由 P0-3 证据反推,过期可调。

## 三、Codex 未覆盖、DSH 补齐的两点（影响开发启动）

### 补齐 1：存量代码「可搬 / 必重写」清单
Codex 说「旧规则可复用」但未给边界。DSH 明确定界：

| 类别 | 处置 | 依据 |
|---|---|---|
| M0 队列/租约/错误码/风控、`pricing/compliance/listing_gate` 规则、M1 采集踩坑记录 | **搬运**（改写进新 schema） | 高置信、非骨架 |
| `feedback.py`/`ad_backfill.py` 的交换文件**契约** | **保留契约**，但重写进流程状态机 | 它是正确数据契约，缺的是自动推进 |
| M2 materials 采集、M3 真实生成、M4 真实写入、M5 投放执行 | **新写**，不搬 mock/骨架 | 复核已证为骨架/占位 |
| `app_config` 同名异义、`_*.py` 24 根级脚本 | **丢弃/重命名** | 历史债 |

### 补齐 2：开发启动的「第一棒」不是搭脚手架，而是先可观测
P0-0 边界冻结必须把 **`mode/provider/model/source/evidence` 强制字段** 定进 schema 与所有外部动作契约，而不是后补——这避免新系统重蹈半成品「把 mock 当已上线」的覆辙。DSH 主张这进 P0-0 验收，而非 P1。

## 四、最终开发方案骨架（供 round-04 拆任务）

| 阶段 | 交付物 | 硬验收（非 mock 计为成功） |
|---|---|---|
| **P0-0 边界冻结** | 新数据字典、tenant/account/shop + 素材绑定模型、错误码/状态机、证据字段、外部动作 read/write/凭证/闸门/回滚契约 | 架构评审过;每个外部动作带证据字段与人工闸门;无「未证实完成」 |
| **P0-1 可演进基座** | 单 Postgres schema + 统一 migration(P0-0 落库) + schema version 检查 + `secret_store` 本地实现 + 认证/审计 + 流程 run/step 表 | 空库/升级/降级/旧样本导入演练过;跨 tenant 查询与跨账号环境访问被测试拒绝 |
| **P0-2 回读领域闭环** | 两次快照模型、解析版本、ROI 计算、回写幂等、`REPORT_MANUAL` 队列、流程/队列协作 | 固定输入下快照去重/窗口/重试/人工确认/回写审计全过(离线逻辑证据) |
| **P0-3 真实只读回读** | M5 CDP 连接、账号级 profile、报表页选择器/探活、快照抓取留证、限流熔断 | **对既存投放取得两次真实快照**;解析率/证据/登录失效/page_changed 跌落可复现;未创建或修改投放 |
| **P0-3.5 M4 契约核对**(新增) | OpenAPI 8/9 业务接口路径与字段核对;决定主链可用性 | 每接口给出「官方路径+字段样例+是否可用」;据此定上架主/兜轨 |
| **P0-4 最小真实写入闭环** | 依 P0-3.5:M4 一商品真实创建/审核/链接(主链或真机兜底轨) + M5 一项小额托管 + 复用 P0-3/2 回写 ROI | 每写入有人审确认+幂等+回滚;两次真实快照成功回写;任一步可暂停/全停 |
| **P1 规模化** | 多店调度、账号级限速/冷却/熔断、素材授权复用、真实生成/上传、生产鉴权 | 至少两店、同账号共享环境与跨账号隔离均过;mock/真实在 UI 与审计可区分 |
| **P2 治理** | 旧规则/数据选择性迁移、脚本归档、CI、依赖锁定、备份/恢复、运行手册 | 迁移/恢复/CI/lint/test/migration 检查/版本标签全过 |

> 关键调整 vs Codex round-02：
> 1. 插入 **P0-3.5 M4 契约核对** 作为独立里程碑（Codex 把它并进 P0-4，DSH 主张拆出以便「主/兜轨决策」不阻塞回读）。
> 2. 明确 **P0-3 只做报表只读回读**，不碰上架 UI（修正措辞混淆）。
> 3. 凭证存储一期限定为本地加密文件 + `secret_store` 抽象（不提前上 Vault）。
> 4. `mode/provider/model/source/evidence` 进 P0-0/P0-1，而非 P1。
